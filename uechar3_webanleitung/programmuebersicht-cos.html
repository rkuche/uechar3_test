Programmübersicht COS

Das COS-System (Central-Operating-System) ist die zentrale Steuerungs-, Überwachungs- und Kommunikationseinheit der Ladesäule.

Es basiert auf Node-RED und übernimmt die Hauptlogik sämtlicher Softwareprozesse: Autorisierung, Messwertverarbeitung, Leistungselektroniksteuerung, Ui-Steuerung, Fehlerhandling, Logging, Zeitsynchronisation, Parametermanagement und System-Monitoring.

Der Zugriff erfolgt über:

http://192.168.24.10:1880

Mit den Benutzerrollen:

  • Configurator → Leserechte
  • Developer → Vollzugriff

Allgemeine Funktionen

Diese Funtionsgruppe enthält alle Flows, die den grundlegenden Betrieb des Systems sicherstellen. Sie umfassen:

  • Dashboard Nutzerverwalter (5.1.1)
  • Dashboard Parameterverwaltung (5.1.2)
  • Dashboard Whitelistverwaltung (5.1.3)
  • Dashboard COS-Monitoring (5.1.4)
  • Dashboard Neustart-Funktionen (5.1.5)
  • Dashboard Maintanance-Funktion (5.1.6)
  • Dashboard Updater-Funktion (5.1.7)
  • Meldungsverwaltung/-archivierung (5.1.8)
  • Zeitsynchronisation des COS (5.1.9)
  • Autorisierungsfunktionen (5.1.10)
  • Websocket Ladekommunikation (5.1.11)

001_service_ui_user_control

Aufgabe: Benutzersteuerung, UI-Freigaben und Rollenhandling

Funktionsumfang:

  • Verwaltung von Login/Logout
  • Prüfung der Benutzerrolle (Operator, Service, Configurator)
  • Ein-/Ausblenden von UI-Elementen anhand der Rechte
  • Automatischer Logout nach 30min
  • Ausblenden sensibler Einstellungen bei aktiven Ladevorgang

Der Flow stellt sicher, dass immer nur zulässige Bereiche sichtbar sind und Bedienfelder im laufenden Betrieb gesperrt werden.

001_parameters_v1_0

Aufgabe: Aufbau, Bereitstellung und Verarbeitung aller Systemparameter.

Funktionsumfang:

  • Generiert vier vollständige Parametergruppen
  • Frontend (Display-Einstellungen)
  • Payment System ((Zahlungsparameter)
  • Authorisation (RFID-Freigaben)
  • Powermodul (Leistungseinstellungen)
  • Stellt die Parameter dem Dashboard bereit
  • Jeder Parameter wird in einem festen Objektformat erzeugt:
{
    "param_key": "",                //name des Parameters
    "param_value": "",              //Startwert des Parameter 
    "label": "",                    //Anzeigewert im Dashboard
    "param_rows": 1,                //Anzahl der Reihen im Dashboard
    "required": 1,                  //Erforderlich
    "param_type": param_type[0],    //Eingabemethode Dashboard
    "default_value": "",            //Standardwert des Parameters
    "grup": 1,                      //Parametergruppe
    "position_in_grup": 1,          //Position in der Gruppe (Dashboard)
    "access_lvl": 1                 //Zugriff operator=1; servie=2; configurator=10 
}
  • Ausgabe:
  • Logging aller Parameteränderungen
  • Trigger für Parameterinitialisierung/-änderung je Gruppe

001_param_whitelits_v0_0

Aufgabe: Verwaltung der RFID-Whitelist inkl. Backend-Synchronisation.

Funktionsumfang:

  • Speichert alle Token in einer SQL-Datenbank, die permanent im Hintergrund gepflegt wird
  • Dashboard erlaubt:
  • Manuelles Eintragen
  • Manuelles Löschen
  • Aktualisieren der Listen
  • Backend-Aktionen werden automatisch übernommen:
  • Akzeptierter Token → wird gespeichert
  • Abgelehnter Token → wird entfernt (falls vorhanden)
  • Eingänge:
  • Whitelist-Freigabe
  • Letzter gelesener RFID-Token
  • Refresh Trigger
  • Backend-Token-Status

001_cos_condition_monitoring_v0_0

Aufgabe: Überwachen der COS-Systemressourcen.

Überwachte Werte (Sekundentakt):

  • CPU-Temperatur
  • CPU-Last
  • Arbeitsspeicher
  • Interner Speicher

Funktionalität:

  • Meldet automatisch Fehlerzustände, sobald Grenzwerte überschritten werden.
  • Übertragt alle Werte an das Dashboard (COS-Conditions)

001_restart_charger

Aufgabe: Steuerung aller Neustartmechanismen (Hardware und Software)

Funktionsumfang:

  • Freigabelogik: Neustarts sind nur möglich, wenn beide Ladepunkte NICHT in CP-State C sind
  • Hardware-Neustart:
  • Router-Ausgang wird per http-GET aktiviert
  • vSECC und Energiezähler werden 10s stromlos geschalten
  • Neustartwird geloggt
  • Software-Neustart
  • Sendet Befehl „Sudo reboot“ an das COS
  • Startet nur die Software neu, nicht die Peripherie

Einsatzgebiete: Kommunikationsfehler, Hänger im System, Reset von Zählern oder Controller.

001_maintanance

Aufgabe: Datenbankwartung und Aktivierung/Deaktivierung Wartungsanzeige

Funktionsumfang:

  • Startet die Wartung alle 4 Stunden, sofern kein Ladepunkt im Zustand C ist.
  • Beschränkt die Logdatenbank auf max. 250000 Einträge, um die Systemstabilität zu garantieren.
  • Über das Maintenance-Dashboard können die Ladepunkte in Wartung versetzt werden

001_updater

Aufgabe: Koordination der Updateprozesse für COS und Touch-Panel

Funktionsumfang:

  • Prüft den CP-State → Update nur, wenn kein Ladevorgang aktiv ist
  • Sucht nach neue Updates
  • Leitet Updateinformationen an das Dashboard weiter

001_error_status_v1_0

Aufgabe: zentrale Fehlererfassung, -verarbeitung, -weiterleitung

Funktionsumfang:

  • Speichert Fehler und Meldungen über sp_insert_log
  • Sammelt:
  • Node-RED-Fehler
  • Lognachrichten
  • Kritische Fehler der Ladepunkte
  • Erkennt Backend-kritische Fehler über MQTT
  • active_failures
  • report_status_inforamtion
  • sendet Fehlerberichte und Fehlerquittierung an das Backend

001_vsecc_sync_cos_time_v0_1

Aufgabe: Automatische Zeitsynchronisation zwischen COS und vSECC.

Funktionsumfang:

  • Empfängt Zeitstempel vom vSECC
  • Prüft Differenz zur COS-Zeit
  • Bei >5s Differenz:
  • Setzt COS-Zeit per sudo date –set=““
  • Informiert anschließend die Energiezähler über neue Zeit

001_vsecc_authorization_v0_0

Aufgabe: Zentrale Autorisierungslogik für RFID-Karten, Backend-Freigaben und Ladepunktzuordnung.

Eingehende Daten:

  • Neuer RFID-Token
  • EVCC-ID
  • OCPP-Transaktion-ID
  • Charging Athorization State (authorized/deauthorized/pending)
  • Availability-State des Ladepunktes
  • Backend-Token-Status
  • Unassigned Token
  • CP-State des jeweiligen Ladepunktes

Funktionsumfang:

  • Erzeugt und steuert UI-Statuswechsel (Bildwechsel)
  • Startet Autorisierungs-Timeout, zeigt Fehlschläge am Frontend an
  • Prüft jeden Token gegen:
  • Aktive Transaktionen
  • Gültige Backend-Tokens
  • Lokale Whitelist
  • Verarbeitet Stopp-/Abbruchsignale vom Frontend
  • Loggt alle Token- und Statusänderungen

001_vsecc_pepWs_v0_0

Aufgabe: Bidirektionale Websocket-Kommunikation zwischen COS und Ladecontroller vSECC (Ladekommunikation).

Eingehende Daten:

  • IMD-Status
  • Leistungselektronik-Statusinformation
  • Leistungselektronik-Konfigurationsdaten
  • Schützrückmeldungen
  • Digitale Eingänge (d1-d8)
  • Analoge Ausgänge (a1-a2)
  • Temperatureingänge (t1-t9)

Funktionsumfang:

  • Speichert alle eingehende pep_ws-Daten im Flow-Kontext
  • Übersetzt evConnectionState → evCpState, um konsistente Statusinformation bereitzustellen
  • Erzeugt Antwortpakete an pep_ws:
  • Status (aktueller Systemstatus der Leistungselektronik)
  • Dynamic Limits (dynamische Grenzwerte der Leistungselektronik)
  • Configuration (feste Grenzwertdaten der Leistungselektronik)
  • Stellt regelmäßige Abfragen bereit:
  • Analogeingänge (alle 5s)
  • Temperatureingänge (alle 5s)
  • Gibt digitale Eingänge einzeln und als Block an das COS weiter
  • Sendet Schaltbefehle über MQTT an Ladecontroller
  • Loggt alle relevanten Ereignisse und Statuswechsel

Frontend

Das Frontend ist das Touch-Display der Ladesäule. Es kommuniziert über eine lokale Websocket-Verbindung mit dem COS. Alle Benutzeraktionen, UI-Bilder, Pop-Up und Livedaten laufen über den Flow 01_cos_to_frontend_0_0.

010_cos_to_frontend_0_0

Aufgabe: Ermöglicht die Kommunikation zwischen COS und Frontend-Display. Steuert Ui-Zustände, überträgt Live-Daten und verarbeitet Benutzereingaben.

Eingehende Daten:

Alle Benutzereingaben werden über msg.payload.type übertragen:

  • Selected: Benutzer hat einen Ladepunkt ausgewählt (chargePointId wird übermittelt)
  • StopCharging: Nutzer hat das Stoppen des Ladevorgangs bestätigt
  • AbourtAuthorize: Abbruch des Autorisierungsvorgangs
  • AbortPlugCar: Abbruch beim Schritt „Fahrzeug verbinden“
  • AbortStopCharging: Abbruch des Stopp-Dialogs

Ausgehende Daten:

UI-Steuerbefehle: Zustandsbefehle zur Anzeige bestimmter Bilder/Pop-Ups (über msg.payload.type & chargePointId)

  • ShowStopppingCharging: Bild „Ladevorgang beendet“
  • ShowStopCharging: Pop-Up „Ladevorgang beenden“
  • ShowStartingCharging: Bild „Ladevorgang startet“
  • PlugCar: Bild „EV verbinden“
  • AuthorizeFailure: Bild „Autorisierung fehlgeschlagen“
  • Idle: Startbildschirm
  • ShowAuthorize: Bild „Autorisierung“
  • Charging: Bild „Ladebildschirm“
  • UnplugCar: Bild „EV trennen“
  • Faulted: Bild „Fehler“
  • ShowAuthorizeWait: Bild „Warten auf Autorisierung“
  • Plugged/Unplugged: Änderung des Steckerstatus

Frontend-Konfiguration: Beim Start sendet das COS eine vollständige Konfigurationsstruktur

  • frontendConfig: Chargername, Hersteller, Betreiber, Sprache, RFID-Modus, Hotline
  • connectorsConfig: CP1/CP2 Typ, Name
  • paymentSystemConfig: Terminal-IP, Port, E-Mail, Beträge, Preise CP1/CP2, Steuer, Währung

Live-Daten: COS sendet während des Ladevorgangs kontinuierlich Mess-, Status- und Session-Informationen über:

  • ChargingSession: Informationen über Leistung, Strom, Spannung, SOC, Zeit, Energie

Funktionsumfang:

  • Aufbau und Verwaltung der Websocket-Verbindung zum Frontend (127.0.0.1:8090/data)
  • Übertragen aller UI-Zustände, Bilder und Pop-Ups
  • Übertragen der kompletten Frontend-konfiguration bei Systemstart/Parameteränderung
  • Übermitteln von Live-Daten während des Ladevorgangs
  • Empfangen und Weiterleiten aller Benutzeraktionen
  • Durchgängiges Logging aller Ereignisse

Messungen

Die folgenden Flows übernehmen die vollständige Kommunikation, Verarbeitung und Bereitstellung der Messwertdaten der AST-DC650-Zähler für CP1 und CP2.

060_ast_dc_v1_0_cp1 & 060_ast_dc_v1_0_cp2

Aufgabe: Realisieren die Anbindung der Energiezähler über http-API und MQTT.

Eingehende Nachrichten:

Link-in:

  • device time changed: Zeitsynchronisation

MQTT:

  • vsecc/connector/#/ev/cp_state
  • vsecc/connector/#/em/measurement_control
  • vsecc/connector/#/status/evse_id_string
  • vsecc/connector/#/ocpp/ev_authorization_token
  • vsecc/connector/#/ocpp/transaction_id
  • vsecc/tariff
  • vsecc/firmware_version
  • vsecc/readiness
  • vsecc/connector/#/status/components/active_failures

Ausgehende Nachrichten:

Link-out:

  • report_resolution: Meldung einer Fehlerauflösung an nachgelagertes Fehlerhandling
  • report_failure: Fehlerereignis an das Fehlerhandling
  • legal_data: Trigger, dass Legal-Data vom Zähler empfangen wurden
  • update dashboard live measurement: Live-Messwerte für das Dashboard
  • legal data for dashboard: strukturierte Legal-Data für das Dashboard
  • logs: Logeinträge zur Protokollierung

MQTT:

  • vsecc/connector/#/em/unsigned_reading
  • vsecc/connector/#/em/measurement_status
  • vsecc/connector/#/em/signed_reading

Funktionsumfang:

  • Init & Setup: Legt Protokoll, IP-Adresse, API-Version, CP-Nr., Basis-URL im Flow-Kontext ab und stellt die drei erforderlichen Initial-Request Zeit (PUT), Public Key (GET) und Version (GET) in die Queue.
  • Zyklen: Aktiviert cyclic gate nach Abschluss der Initialisierung und startet im Sekundentakt die Anfragen für Livemeasurement, Fehlerstatus und Gerätestatus.
  • Response Handling: Antworten mit Status-Code 200 werden übernommen, gespeichert und weitergegeben.
  • Availability: Überprüft alle 10s, ob der Zähler verfügbar ist. Bei mehr als 3 aufeinanderfolgenden fehlerhaften Livemeasurement-Antworten wird der Zähler als nicht verfügbar markiert.
  • Measurement Control: Leitet die Steuerkommandos (MQTT: measurement_control) an den Zähler weiter. Beinhalt Start, Stopp OCMF-Datenanfrage.
  • Queue Abarbeitung: Arbeit die Queue mit 10 Request-Vorgängen pro Sekunde ab. Fehlerhafte Antworten werden bis zu dreimal erneut gesendet.

Schutzfunktionen

Die Schutzfunktionen überwachen die sicherheitsrelevante Komponenten der Ladeeinrichtung und stellen sicher, dass fehlerhafte Zustände, Isolationsabweichungen und Kommunikationsstörungen frühzeitig erkannt werden.

100_iso_bender_cha425_v0_1

Aufgabe: Implementiert das Modbus-Interface für IMDs und stellt Isolations- sowie Gerätestatus der Ladepunkte bereit.

Eingehende Nachrichten:

  • connection state: CP-State des jeweiligen Ladepunktes
  • charging state: Ladephase des Ladepunkts
  • contactor state: Rückmeldung der Schützgruppe des Ladepunktes

Ausgehende Nachrichten:

  • status updated: Isometer-Statusinformation

Funktionsumfang:

  • Kontextfunktionen:
  • handleIsoMeasurement: Übersetzt Kanalbezeichnung und Alarmtyp in den Isolations-Status und protokolliert Statuswechsel.
  • timeoutModbusFail: Setzt ein Timeout bei ausbleibender Antwort.
  • checkAvailability: Setzt das Timeout bei Antwort zurück und meldet Ausfälle des IMDs.
  • Statusabfrage: Erstellt eine Statusanforderung mit der Funktion 3 und sendet diese über den Modbus Flex Getter.
  • Gerätetest: Sendet Steuerbefehl mit der Funktion 16 zur Geräteüberprüfung und sendet diese über den Modbus Flex Write, wenn die jeweilige Schützgrüppe geschlossen ist und CableCheck aktiv ist.
  • Messdatenverarbeitung: splite_measurement_values teilt das Datenpaket. parse_measurement dekodiert die Pakete und setzt die Gerätetest-Flag zurück.
  • Statussetzung: get imd status aktualisiert die Isolations-Statusinformation. Set isoStatus during cableCheck erzwingt invalid, bis der Gerätetest durchgeführt wurde.

Powermodul

Die Powermodul-Flows steuern Schütze, Leistungsmodulgruppen und Zusammenschaltung (CCM) der Ladepunkte. Sie erfassen Zustände, setzten Sollwerte, überwachen Grenzwerte und leiten sicherheits- und leistungsrelevante Informationen an das COS weiter.

150_contactor_v0_1

Aufgabe: Steuerung der Schützgruppen für CP1, CP2 und CCM. Auswertung der Rückmeldesignale und Umsetzung der gültigen Schaltbedingungen.

Eingehende Nachrichten:

  • digital In updated: Rückmeldung der Schütze
  • temp status: Steckertemperaturen CP1/CP2
  • pep state updated: Schaltbefehl und CP-State vom Ladecontroller
  • pm status info updated: Statusinformation der Leistungselektronik
  • contactor state updated: CCM-Schaltbefehl

Ausgehende Nachrichten:

  • contactors updated: aktualisierter Schützstatus für das Dashboard
  • log: Protokollierung des Schützstatus
  • contactors CPx updated: Schaltzustand (0/1), ID und Ausgangsnummer zur Ansteuerung der Schütze

Funktionsumfang:

  • Kontextfunktionen:
  • computeConStatus: Prüft, ob eine Schützgruppe geschaltet werden darf, basiert auf CP-State, Rückmeldungen und Strom.
  • setConState: Setzt Schützstatus.
  • checkFdbackState: Überprüft, ob die Rückmeldung für die Ansteuerung der Schütze ankommt.
  • compute ccm contactor status: Prüft CCM-Schaltbedingungen, CP-State und Rückmeldungen der Ladepunkte.

150_combine_charging_modules_v0_0

Aufgabe: Implementiert die CCM-Logik zur Zusammenschaltung der Leistungsmodulgruppen.

Eingehende Nachrichten:

  • connection state updated: CP-State des Ladepunkts
  • contactor state feedback: Rückmeldung der Schützgruppen
  • status info updated: Statusinformation der Leistugselektronik
  • isolation state updated: Isolations-Statusinformation
  • request: Anforderung für die Zusammenschaltung

Ausgehende Nachrichten:

  • request result updated: CCM-Freigabe (true/false)
  • enMdlRequest updated: Modulanfragen für Zusammenschaltung (reqModulNo, evChargingState, targetVoltage, targetCurrent)
  • contactor state updated: Schaltbefehl für CCM-Schütz (0/1)

Funktionsumfang:

  • check cpState: CCM nur zulässig, wenn beide Ladepunkte in gültigen CP-State sind.
  • check pm operation state: Beide Leistungsgruppen müssen operativ sein.
  • check contactor state: Prüft die Rückmeldungen der relevanten Schütze.
  • set requested module data: Erstellt Payload für Modulanforderung.
  • close/open contactor: Schaltet CCM-Schütze basierend auf Spannungstoleranzen und Stromgrenzen.
  • check voltage diff/check current tolerance: Überwacht die entsprechenden Werte bis sie im Toleranzbereich liegen.

Funktionsumfang:

  • check time interval/set power reduction: Wendet zeitbasierte/permanente Leistungsreduktion an.

150_pepWs_to_pm_mapper_v0_0

Aufgabe: Daten-Mapper zwischen Ladecontroller-Websocket (PEP-WS) und Leistungselektronik der beider Ladepunkt, Richtung Leistungselektronik.

Eingehende Nachrichten:

  • pep targetValues updated: Sollwerte vom EV
  • pep connectionState updated: Verbindungsinformationen des EVs
  • request add modules: CCM-Anfroderungen

Ausgehende Nachrichten:

  • values updated: geänderte EV-Sollwerte
  • ev values updated: geänderte EV-Verbindungsinformationen

Funktionsumfang:

  • Kontextfunktionen:
  • processConnection: Leitet Werte abhängig vom CCM-Status an die richtige Modulgruppe weiter. Bei CCM aktiv werden Sollwerte an beide Gruppen verteilt, inaktiv nur an die zugehörige Gruppe.

150_huawei_group_cp1 & 150_huawei_group_cp2

Aufgabe: Steuert und überwacht die Leistungsmodulgruppen für CP1 und CP2, inkl. Sollwertsetzung, Modulanzahlberechnung, Status-Dekodierung und CAN-Kommunikation.

Eingehende Nachrichten:

  • parameter settings powermodule: Konfigurierte Modulanzahl, CCM-Freischaltung
  • values updated: Sollwerte und CCM-Anfragen
  • ev values updated: EV-Verbindungsinformationen
  • cp1/2 status info: Verfügbare Module der anderen Gruppe
  • request result updated: CCM-Freigabe
  • status change updated: Aktuelle Modulverfügbarkeit
  • incoming can message: CAN-Daten der Gruppe

Ausgehende Nachrichten:

  • CAN message: Generierte CAN-Nachrichten
  • Huawei charge logs: Logdaten
  • status_info_updated: Statusinformationen der Leistungselektronik
  • config updated: Konfiguration der Leistungselektronik
  • module data: Modulinformationen (Modul 1-6)
  • mdl request: Anforderung weiterer Module

Funktionsumfang:

  • Kontextfunktionen:
  • handleStatusErrors: Logt die Status-/Errorbits der einzelnen Module.
  • setTargetValue: Setzt die Sollwerte für die CAN-Nachricht
  • parse message / CAN filters: Dekodiert gültige CAN-Frames, speichert diese und verwirft ungültige.
  • check min/max values: Ermittelt Grenzwerte der gesamten Gruppe.
  • calc group output values: Berechnet die aktuelle Gesamtwerte (Spannung, Strom) der Gruppe.
  • set group operation status: Bestimmt die Verfügbarkeit der Gruppe anhand der verfügbaren Module.
  • sort runtimes: Sortiert die Module nach der Betriebslaufzeit.
  • set optimal module number: Berechnet die optimale Modulanzahl basierend auf den Zielstrom.
  • set operation mode / set target values: Erzeugt CAN-Schalt- und Sollwertnachrichten.
  • request-Zyklen: Fordert optimalen Strom, Batch-Daten (Status, Fehler, gesetzte Werte) alle 1 Sekunde an.
  • event-Anfragen: Fordert Laufzeit und Grenzwert bei State-Wechsel an.
